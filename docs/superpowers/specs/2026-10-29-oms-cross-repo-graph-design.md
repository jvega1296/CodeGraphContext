## Intent and why

Javier is a Sr. Full Stack Engineer on AutoZone's OMS/VDP team, working across 60+ microservices (Java/Spring Boot) connected by GCP Pub/Sub, internal HTTP APIs, and shared GCP infrastructure (Terraform). He wants one navigable graph — in CodeGraphContext (CGC), exposed to Claude Code via MCP — that can trace a business flow (e.g. `createOrder`) end-to-end across repo and infrastructure boundaries, do risk-scored blast-radius analysis approaching the quality of a reference tool (code-review-graph), and do hybrid search, all centralized in one tool instead of split across CGC + neo-rag + manual reading of Terraform/K8s configs.

Two upstream PRs CGC already has (merged into this fork's `main`) looked like they'd get most of the way there: PR #1728 (cross-repo wire-coupling: Kafka/HTTP/gRPC producer-consumer edges) and PR #1298 (`analyze_impact`: blast-radius/risk-scoring). Investigation found they don't compose, and neither is deep enough on its own. This design covers what it actually takes to deliver what Javier wants.

## Goals

1. `analyze_impact`-style traversal that actually crosses GCP Pub/Sub producer→consumer boundaries across separate repos, not just Kafka (which none of the real AZ repos use).
2. The traversal also reaches the real Terraform-defined GCP resource behind a Topic/Subscription, not just a code-inferred node floating with no connection to infrastructure.
3. Risk scoring that includes the dimensions that actually predict review risk (test coverage, security sensitivity, caller count, change frequency) — ported from code-review-graph's `changes.py`, translated to Cypher, backend-agnostic.
4. Hybrid search (exact → fuzzy lexical → semantic) fast enough that an AI agent calling these tools as MCP tools doesn't pay unnecessary latency on the common case (agent already knows the identifier).
5. Everything validated against the real, already-indexed AZ repos (`special-order-services`, `oms-order-consumer`, `oms-order-update-consumer`, `terra-projects-oms/az-ordfl-ordrmgmt`), with a concrete, literal acceptance test — not just unit tests in isolation.

## Non-goals (this pass)

- Live GCP introspection (Cartography-style, reading actually-deployed state) — tracked as a separate future project in the vault docs.
- Full code-review-graph fidelity on community detection (real Leiden/igraph), flow/execution-path modeling, and cross-language test-linkage extraction — lightweight proxies only this pass (see Decisions #4).
- K8s `values.yaml`-based stitching for Endpoint nodes (Cloud Run/GKE deployment identity) — Terraform/HCL stitching only this pass; K8s YAML isn't HCL and would need its own extractor, out of scope here.
- Upstreaming any of this back to `CodeGraphContext/CodeGraphContext` — this is a private fork customized for AutoZone's OMS architecture, not intended as a contribution.

## Anti-goals (failure even if it technically runs)

- A traversal that silently stops at a repo or infra boundary without saying so. This is the exact failure mode that motivated the whole project; regressing to it anywhere (new edge types included) is a hard failure.
- Any added latency on the fast/exact search path for calls that never need the fuzzy or semantic tiers.
- A GCP Pub/Sub extractor that only recognizes the one pattern seen in `special-order-services`/`oms-order-consumer` and silently produces nothing — no edge, no warning — for other valid Spring Cloud GCP usages. Silent gaps are worse than loud ones here.

## Ground truth gathered (verified by reading the actual source/code; do not re-derive or assume otherwise)

- **Producer pattern** (`special-order-services`): `com.google.cloud.spring.pubsub.core.PubSubTemplate.publish(...)`, called from a wrapper class `MessagePublisher`/`PublishMessagePubSub`. Spring Cloud GCP, not the raw Google client library.
- **Consumer pattern** (`oms-order-consumer`, `oms-order-update-consumer`): a `@Configuration` class defines a `PubSubInboundChannelAdapter` bean that wires a subscription name — usually a `${az.pubsub.subscription.name}`-style property placeholder, not a literal string — to a Spring Integration `MessageChannel`. A separate class's `@ServiceActivator`-annotated method is the actual function that receives the message. Three hops of indirection, not a single annotation.
- **Terraform** (`terra-projects-oms/az-ordfl-ordrmgmt/*/pubsub.tf`): topics are declared via `module "..._pubsub_config" { topic = "..." }`; each topic's `pull_subscriptions` list carries its own `name` and `service_account` — the service account is the most reliable signal for "who consumes this."
- **PR #1728 (wire-coupling, already merged here)**: `Topic {system, name}`, `Endpoint {protocol, method, path}`. `PRODUCES_TO` and `CONSUMES_FROM` both point *Function → Topic* (same direction) — there is no natural directed chain through a Topic the way `CALLS` chains through callers; crossing producer→consumer needs an explicit bridging pattern, not a longer relationship list. Extractors exist only for Kafka/HTTP/gRPC/Go/Python — confirmed zero GCP Pub/Sub support (`grep` for `google.cloud.pubsub`/`PublisherClient`/`GcpPubSubTemplate` across `src/codegraphcontext/wire/`: no hits).
- **PR #1298 (`analyze_impact`) was NOT merged when this doc was first drafted** — an error in the first draft, caught by builder-check (`git merge-base --is-ancestor pr-1298 main` → no; zero hits for `analyze_impact` anywhere in `src/`). **Fixed**: merged clean (no conflicts) on 2026-10-29, pushed as `55d1eebe..d4856296`. The website UI half of that diff (425 lines, `CodeGraphViewer.tsx`) was kept rather than stripped — it's a working enhancement to the visualizer already set up for this fork, no reason to rip it out.
- **`analyze_impact`'s traversal is upstream-only** (per its own docstring: "propagation upstream"): `MATCH p = (source)-[:CALLS|INHERITS|...]->(target) WHERE target.uid IN $target_uids` finds things that transitively *call into* the target — classic "who breaks if I change this." It does not, and structurally cannot without changes, follow any wire-coupling edge type, **and even with those edge types added it only looks backward, never forward from a producer to what it triggers downstream.** This is a bigger gap than "missing edge types" — see Decisions, Direction question.
- **`hcl.py`**: has generic attribute-reading primitives (`_attributes`, `_literal`, `_value_of`) already, but only stores specific known attributes as node properties today (e.g. `description` → `docstring`). Does not generically capture a `topic`/subscription-identifying attribute as a queryable property. **Correction (builder-check)**: this undersells the gap for `service_account` specifically. `pull_subscriptions` is a list of *objects* (`{name = "...", service_account = "..."}`), and the only existing list-attribute helper, `_literals()`, only walks tuples of bare strings (built for `paths = ["../vpc", "../db"]`) — it returns `[]` silently for a list of objects, not partial data. Reading `topic = "..."` (a plain string attribute) already works with existing primitives; reading `service_account` out of each `pull_subscriptions` entry requires new object-list-walking code that doesn't exist yet. See Decisions for the phasing this implies.
- **No comparable "resolve a cross-class bean wiring" pattern exists to copy for the GCP Pub/Sub consumer side.** `kafka_extractor.py` and `http_extractor.py` were checked in full (builder-check): both are single-file, single-hop regex extractors reading an annotation directly off the method it decorates (`@KafkaListener`, `@GetMapping`). The actual consumer pattern (`PubSubInboundChannelAdapter` bean in one class wiring a channel name that a *different* class's `@ServiceActivator` method binds to) is a cross-class, name-based join with no existing shape in this codebase to borrow — it needs to be designed, not copied. Both halves of the real pattern live in the *same repo* (confirmed: `ListenerConfig.java` and `ListenerService.java` are both in `oms-order-consumer`), so this is a bounded, single-repo, two-pass resolution problem, not a cross-repo one.
- CGC has **zero** existing test-coverage edges, community detection, `is_test` flagging, or security-keyword list anywhere in `src/codegraphcontext/` (confirmed by grep across the whole source tree) — these are new builds if pursued, not ports of something partially there.
- Wire-coupling extraction is wired into `pipeline.py` Phase 6 (gated by `MULTI_REPO_LINKS` env flag): imports `scan_repo_kafka/http/grpc` + `write_wire_edges(writer, kafka_scan=..., http_scan=..., grpc_scan=..., include_ambiguous=...)`. A new GCP Pub/Sub scan needs the same shape, wired in alongside the existing three.
- code-review-graph's own `communities.py` explicitly falls back to file-based grouping when `igraph` isn't installed — precedent that a lightweight proxy is an accepted, documented design choice in the reference project itself, not a corner-cut unique to this fork.
- **Confirmed (not assumed): all indexed repos already land in the same physical graph.** The embedded backend (`database_embedded_kuzu.py`, shared by LadybugDB/KùzuDB) is a true singleton keyed on one `LADYBUGDB_PATH`; `graph_name` is accepted but explicitly ignored ("for interface parity with FalkorDB"). This was never exercised as a hypothesis — it's the same mechanism that produced the file-lock error ("Could not set lock on file: ...\ladybugdb") when two `cgc index` runs were attempted concurrently earlier in this project, which is direct, already-observed proof that every `cgc index` run on this machine, across every repo so far (`oms-commons`, `special-order-services`, `terra-projects-oms/az-ordfl-ordrmgmt`), has been writing to the one shared database file. No new verification needed before relying on it for the acceptance test — it already holds.

## Decisions made (confirmed with Javier in conversation)

1. **GCP Pub/Sub gets a first-class `Subscription` node**, not folded into `Topic`. Schema: `Subscription {name, project_id}`. Edges: `(Topic)-[:HAS_SUBSCRIPTION]->(Subscription)`, `(Function)-[:CONSUMES_FROM]->(Subscription)` (consumer side), `(Function)-[:PRODUCES_TO]->(Topic)` (producer side — unchanged, matches the existing Kafka shape). This is what lets Terraform stitching match by subscription name + `service_account`, the most reliable signal Terraform actually gives us, instead of guessing from topic name alone.
2. **Search is a 3-tier cascade** (exact Cypher → lexical fuzzy via a new SQLite FTS5 sidecar, independent of the graph backend → semantic, local embeddings, only triggered below a result-count threshold), not always-fused RRF. Chosen for query-time speed: CGC is called by an AI agent via MCP, which more often already knows a precise identifier than a human doing exploratory search, so paying an embedding-call cost on every search is wasted work most of the time.
3. **Default local embedding model: `fastembed` / `BAAI/bge-small-en-v1.5` (ONNX, no torch)** — already a supported `CGC_EMBEDDING_MODEL` value, zero new integration cost, zero network dependency, zero per-query cloud latency. Port `_split_identifier`-style preprocessing (snake_case/camelCase/PascalCase splitting) from code-review-graph's `embeddings.py` before embedding — free quality improvement, no runtime cost.
4. **Lightweight proxies for the three schema-heavy risk factors this pass**: module/package-based grouping instead of real Leiden community detection (mirrors code-review-graph's own igraph-unavailable fallback); a naming/co-location heuristic for test-linkage instead of full cross-language test resolution (Java/JUnit is the dominant real case — don't generalize to all 27 CGC-supported languages for this). Full-fidelity versions are an explicit, separate follow-on project, not blocking this one. (Javier: "quiero todo" means all 5 pieces land, not that every sub-factor reaches code-review-graph's exact depth in this pass — confirm this reading is right before building; flagged below as a builder-check item too.)
5. **Security-keyword scoring, caller-count scoring, and churn scoring** (with its full caching/timeout/sticky-unavailable-cache/trailing-window infrastructure) are ported to **full fidelity** — none of these need new schema, so there's no reason to cut corners.
6. **Line-level diff parsing, change-to-node mapping, and the diff-parsing robustness layer** (C-quoted paths, SVN support alongside Git, ref-injection-safety validation, graceful whole-file-scoring degradation with an explicit warning) are ported **in full** — pure Python, backend-agnostic, no reason to skip any of it.
7. Development happens on the fork's `main` directly (already diverged from upstream; not intended to be upstreamed) — no need for worktree isolation to protect an upstream contribution flow. Worktrees may still be useful operationally for running independent pieces in parallel (builder's call).
8. **Acceptance criterion, concrete and literal**: re-index `special-order-services`, `oms-order-consumer`, `oms-order-update-consumer`, and `terra-projects-oms/az-ordfl-ordrmgmt` for real (not mocked), then run the impact/blast-radius tool on `createOrder`/`MessagePublisher.publish` and confirm the result set includes nodes from the consumer repos *and* the Terraform module backing the topic — not just nodes inside `special-order-services`. This is "done," not "unit tests pass in isolation." Run with `direction=both` (see Direction section) — the acceptance test is specifically a "complete picture" question, not a one-sided blast-radius question, so the merged-trace mode is the one that has to work for this to count as done.
9. **Website UI diff from PR #1298 kept, not stripped** — it's a working enhancement to the already-working visualizer, no reason to remove it just because this project's primary interface is MCP tool calls, not the browser UI.

## Direction — resolved with Javier

**Decision: option (a), `direction: "upstream" | "downstream" | "both"` on `analyze_impact`, default `upstream`.**

Javier's framing, which fixes the exact semantics of `both`: changing a validation function in the middle of `createOrder` can break something *before* it in the flow (upstream — what feeds into/depends on this function's contract) *and* something *after* it (downstream — what this function's output drives, including across repos via Pub/Sub). Sometimes he only cares about one side (a narrower, faster review question); sometimes he wants the complete picture.

Implementation consequence this sets, beyond the parameter existing: **`direction=both` must return one connected trace** — true origin through the target to true termination, with the target point identifiable in the middle — not two independent, disconnected upstream/downstream result sets the caller has to mentally stitch back together. That merged-single-trace requirement is the part of this decision that actually constrains the implementation; the parameter itself is the easy part.

## What's left to the builder

- Exact Cypher form for the Topic→Subscription→Function bridging pattern (separate `MATCH`/`UNION` vs. `OPTIONAL MATCH` vs. two queries merged in Python) — verify against the actually-installed LadybugDB's Cypher support before committing to a specific clause; don't assume parity with Neo4j's dialect.
- Exact static-analysis approach for the 3-hop consumer pattern (`PubSubInboundChannelAdapter` bean → `MessageChannel` → `@ServiceActivator` method). **Corrected scope (builder-check)**: there is no existing comparable shape in `kafka_extractor.py`/`http_extractor.py` to copy — both are single-hop, same-method annotation reads. This is genuinely novel, bounded single-repo, two-pass design work (confirmed both halves of the real pattern live in one repo, e.g. `ListenerConfig.java` + `ListenerService.java` in `oms-order-consumer`): pass 1 collects bean-defined channel names (and whatever identifies them — `@Qualifier` constant, bean method name, etc.), pass 2 matches `@ServiceActivator(inputChannel = ...)` methods against those names. Design the join key deliberately; don't assume a trivial string match will be unambiguous across all four OMS consumer repos without checking each one first.
- Whether unresolved `${...}` property placeholders (subscription names) get resolved by reading `application*.properties`/`.yml` (full fidelity) or stored as the raw placeholder with an unresolved flag (cheaper, deferred) — check whether `config_scanner.py`/`config_values.py` (already present in `src/codegraphcontext/wire/`) already solve exactly this for other wire features before building something new; lean toward reusing if so.
- **New (builder-check)**: `hcl.py`'s `_literals()` only handles string-element lists; `pull_subscriptions` is a list of objects (`name`, `service_account`, ...). Reading the subscription's bare `topic = "..."` attribute works today (basic Topic-level stitching is buildable immediately); reading `service_account` per subscription needs new object-list-walking code in the HCL parser. Phase these: ship topic-name-only stitching first, add the `service_account` cross-check as a fast-follow once the object-list parsing exists — don't block the whole stitching piece on the harder parser work.
- Exact module/package-boundary heuristic for the lightweight community proxy.
- Exact heuristic for the lightweight test-linkage proxy (naming convention, co-location, both) — scope to Java/JUnit as the dominant real case here, not generically to all supported languages.
- Where the FTS5 sidecar database file lives relative to the existing `.codegraphcontext` config directory — follow existing conventions in `config_manager.py`.
- Full test suite shape: unit tests follow CGC's existing conventions (`tests/unit/...`, the mock-driver pattern already used in PR #1298's own tests); the end-to-end acceptance test (Decision #8) is additionally required as its own clearly-separate integration-style test/script against the real indexed repos, not folded into more unit mocks.
- Branch/worktree execution strategy for the 5 pieces — the existing roadmap doc's sequencing (pieces 1 + 2 parallelizable, piece 3 depends on piece 1 existing) still holds; whether to literally use `git worktree` per piece or just sequence commits on `main` is the builder's call.

## Approaches considered

**Subscription modeling**: (a) reuse `Topic` for subscriptions too — rejected, loses the Terraform-matching fidelity that's the whole point of piece 3; (b) first-class `Subscription` node — **chosen**; (c) skip the Topic/Subscription distinction, model GCP Pub/Sub exactly like Kafka — rejected, defeats the actual cross-repo tracing goal since Terraform's most reliable consumer signal (`service_account` on a subscription) would have nothing to attach to.

**Search architecture**: (a) full RRF fusion ported verbatim from code-review-graph's `hybrid_search` — rejected, pays an embedding-call cost on every single search regardless of need, directly conflicts with the stated speed priority; (b) 3-tier cascade — **chosen**; (c) exact search only, no semantic tier at all — rejected, Javier explicitly wants to deprecate neo-rag and centralize semantic search inside CGC.

**Risk-scoring schema-heavy items**: (a) full code-review-graph fidelity (real Leiden via `igraph` export, full flow/execution-path modeling, full cross-language test resolution) — rejected for this pass, each of these three is a multi-week project on its own and would swallow the whole effort; (b) lightweight proxies now, full fidelity as an explicit separate follow-on — **chosen**; (c) skip entirely — rejected, Javier asked for everything, not a subset chosen by checkbox.
